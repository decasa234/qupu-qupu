# Reusable Explainer Pool — Design

- **Date:** 2026-06-16
- **Status:** Approved (brainstorming) → ready for implementation plan
- **Topic:** Parameterize WMI illustration+explainer pairs into a reusable, ID'd,
  described pool so future paper conversions reuse from it instead of rebuilding.

## Problem

Converting a past paper currently produces a **bespoke, one-off** illustration +
explainer per visual question (~1000 components in
`src/components/wmi/paperQuestions/`). The same animation shapes recur constantly
(count-one-by-one, cube-stack layer count, balance/substitution, arrow-grid path,
clock read, sequence-next…), but each conversion rebuilds them from scratch. The
existing reuse aid — grep `INDEX.md` — only helps when the *exact* same problem
recurs, because the components aren't parameterized and the catalog isn't oriented
around "what shape does this solve."

We want: (1) genuinely **parameterized** explainer animations for the
high-recurrence shapes (true zero-code reuse), and (2) an **ID'd, summarized
catalog** the next AI reads *first* to quickly decide whether a suitable animation
already exists.

## Goals

- A pool entry = an **illustration + explainer pair** (they share the SVG
  primitive and are reused together).
- **Tiered reuse:** a discovery catalog over *every* pair (copy-adapt the closest)
  **plus** true parameterized **templates** for the high-recurrence shapes
  (pick id + pass params, no new `.tsx`).
- Every entry has a stable **id**, a one-line **summary**, and a **`useWhen`**
  match signal. The catalog is **auto-generated** (never hand-maintained, never
  stale) and **scannable** (read-first file stays small as bespoke count grows).
- Matching is done by the **converting AI reading the catalog** — no runtime
  matching engine, no DB, no auto-suggestion service.

## Non-goals / scope guardrails (YAGNI)

- **No** DB tables, runtime matching engine, or AI suggestion service.
- **No** retrofitting all ~1000 bespoke components into templates. Bespoke stays
  bespoke and remains discoverable via the catalog. Only high-recurrence shapes
  become templates.
- **No** change to the separate **concept-generation engine**
  (`api/services/wmi/concepts/`). Templates may *wrap* concept explainer
  components, but paper questions are not pushed through `generate()`/`render()`
  (concepts emit whole generated questions; paper questions already have
  body/choices/answer).

## Background (relevant existing code)

- **Two explainer systems today:**
  - *Concept explainers* (`api/services/wmi/concepts/<slug>/index.ts` +
    `src/components/wmi/concepts/explainers/`): already parameterized
    (`paramsSchema` + `render(params)`), slug-ID'd, `meta`-described, registry-backed
    (`EXPLAINERS`). Built for **generated practice**, ~60 concepts.
  - *Paper-question explainers* (`paperQuestions/*Explainer.tsx`): bespoke, one-off,
    keyed by paper code in `registry.ts` (`VISUALS`), catalogued in `INDEX.md`.
- **`ExplainerProps`** already includes `params: unknown` and `correctAnswer`
  (`concepts/explainers/registry.ts`). The contract supports params; bespoke paper
  explainers just ignore them.
- **`WmiQuestionView.tsx:183`** renders paper explainers with hardcoded
  `params={{}} correctAnswer=""` — this is the one plumbing change templates need.
  The concept-illustration path in the same file already passes real `params`.
- **`db/seed/wmi/build-visual-index.ts`** generates `INDEX.md` by parsing each
  component's header comment, aria-labels, and registry wiring → the catalog
  generator to extend.
- **`makeTryCheckExplainer`** (`paperQuestions/tryCheckExplainers.ts`) is already a
  data-driven factory (intro/items/final) — an existing template pattern that
  covers most non-figure deduction questions.
- Zod is already a dependency (concept paramsSchemas use it).

## Decisions (from brainstorming)

| Question | Decision |
|---|---|
| What is the pool made of? | A **new, paper-shaped template layer** that borrows concept patterns (typed params, registry, co-located meta) but not the concept generation engine; templates may wrap concept components. |
| Reuse fidelity | **Tiered: both** — catalog everything + true parameterized templates for high-recurrence shapes. |
| Unit of reuse | **Illustration + explainer pair.** |
| Approach | **A — Catalog + parameterized template registry** (extend `build-visual-index.ts`; don't bend the concept engine). |

## Architecture — four pieces

1. **`meta` block** — a typed `export const meta = {…}` co-located in each poolable
   illustration file (it owns the primitive). Source of truth for the catalog.
2. **Pool catalog** — `EXPLAINER_POOL.md` (AI read-first) + `pool.json` (machine),
   auto-generated by the extended indexer.
3. **Template registry** — curated parameterized pairs (`status: "template"`) in
   `src/components/wmi/paperQuestions/templates/`, resolvable by `templateId`.
4. **Params plumbing** — seed JSON carries `{ templateId, params }` per reused
   question; `registry.ts` + `WmiQuestionView` thread `params` + `answer` into the
   illustration and explainer.

## Catalog data model

Each poolable pair declares (co-located in the illustration `.tsx`):

| field | example | purpose |
|---|---|---|
| `id` | `cube-layer-count` | stable pool key (kebab, **shape-named**, not paper-coded) |
| `title` | "Isometric cube/stack layer count" | human label |
| `summary` | "Counts cubes in an isometric stack layer-by-layer with a running total." | the one-liner the AI scans |
| `useWhen` | "How many cubes/cylinders are in a 3-D pile, incl. hidden ones." | match signal |
| `tags` | `["counting","3d","isometric"]` | grep/filter |
| `grades` | `[1,2,3]` | applicability |
| `status` | `"template"` \| `"bespoke"` | true-reuse vs copy-adapt |
| `params` | Zod schema (templates only) | what to pass to reuse |
| `usedBy` | `["WMI-19P1A-Q4","WMI-20P3A-Q20"]` | **auto-filled by indexer** from registry; shows recurrence |

Generator behavior (extends `build-visual-index.ts`):
- For files with a `meta` block → use it.
- For the ~1000 existing bespoke files **without** `meta` → fall back to the current
  header-comment Description + name-derived keywords (same as `INDEX.md` today).
  So the catalog is rich on day one with **zero** hand-editing.
- Emit:
  - **`EXPLAINER_POOL.md`** (read-first): **templates fully described**
    (useWhen + param shape + copy-paste example), then **bespoke as one-liners
    grouped by tag**. Stays scannable as bespoke grows into the thousands.
  - **`pool.json`**: full structured data for tooling.
  - Full bespoke detail remains in `INDEX.md` (unchanged role).
- Deterministic: CI regenerates and asserts `git diff` is clean.

## Template contract + params data flow

A **template** = a parameterized illustration primitive + an explainer that both
read a typed `params` instead of hardcoding. Example: `CubeLayerCountTemplate`,
`params: { layers: number[]; unit?: "cube" | "cylinder" }`, with `answer` coming
from the question.

Reuse flow at conversion time:

```
seed question:
  { ..., "visual": { "templateId": "cube-layer-count",
                     "params": { "layers": [8,7,4], "unit": "cube" } } }
        │
registry.ts:    templateId → { Illustration, Explainer }   (TEMPLATES map)
        │
WmiQuestionView: params = question.visual.params,  correctAnswer = question.answer
        │
component:      renders figure + animation from params — no new .tsx
```

- **One plumbing change** in `WmiQuestionView`: when `question.visual?.templateId`
  is set, resolve via `TEMPLATES` and pass real `params` + `question.answer`;
  otherwise current behavior (resolve `VISUALS[code]`, params ignored). Fully
  backward compatible — all ~1000 bespoke components keep working unchanged.
- **Validation:** at seed load (`db/seed/wmi` + `validate.ts`), if a question has
  `visual.templateId`, import that template's exported Zod `params` schema and
  validate `visual.params`. A bad reuse fails `wmi:validate`, not at runtime.
- `templateId` must exist in the `TEMPLATES` registry (validated too).

## Reuse workflow (`wmi-paper-conversion` skill change)

Add a **pool reuse pass** in Phase 3 (Enrich), before any component is built. For
each `needsVisual` question the converting AI:

1. Reads `EXPLAINER_POOL.md` (templates section first).
2. **Template match** → write `{ templateId, params }` into the seed JSON. No
   `.tsx` built.
3. **Bespoke near-match** → copy-adapt the closest catalogued pair (today's
   reuse-before-build, now matched on `useWhen`/tags).
4. **No match** → build bespoke as today, **and include a `meta` block** so the
   indexer auto-adds it to the catalog.

Role-agent prompt change (one line): "grep INDEX.md" → "read `EXPLAINER_POOL.md`;
prefer a template; if you build new, include a `meta` block."

**Promotion report:** a script lists shapes with ≥3 bespoke instances (by tag /
name cluster) not yet templated → the queue for new templates.

## Initial template set (~14)

Chosen by recurrence; most **wrap components that already exist**, so this is
largely metadata + a thin param adapter, not new animation work.

- **Wrap existing concept explainers:** `clock-read`, `cube/stack-layer-count`
  (block-count-3d), `balance/scale-read`, `arrow-grid-path` (grid-path-steps),
  `count-shapes-in-figure`, `maze-shortest-path`, `bar-chart/pictograph-compare`,
  `dice-net-fold` / `dice-opposite-faces`, `fraction-of-region`,
  `number-line-jumps`.
- **Formalize the existing factory:** `try-and-eliminate` (`makeTryCheckExplainer`
  — covers most non-figure deduction questions).
- **Build new, paper-shaped** (high recurrence, not cleanly a concept):
  `count-one-by-one` (figure enumeration with running counter),
  `balance-substitution` (A = nB chains), `symbol-substitution / shape-equation`.

## Testing

- `meta` validation: every block parses; `id`s unique; required fields present
  (new check in `wmi:validate`).
- Template params validated against their Zod schema at seed load.
- SSR smoke (extend existing): render each template with sample params + each
  question that references a template with its real params.
- Catalog determinism: CI regenerates `EXPLAINER_POOL.md`/`pool.json`, asserts
  `git diff` clean.

## Rollout (each step shippable on its own)

1. **Indexer** → emit `EXPLAINER_POOL.md` + `pool.json` (header-comment fallback
   for existing files). Zero behavior change; immediate AI value.
2. **Params plumbing**: `WmiQuestionView` template path; seed schema gains optional
   `visual.{templateId,params}`; load-time validation.
3. **Build the ~14 templates** (mostly wrappers) with `meta`.
4. **Update `wmi-paper-conversion`** skill (reuse pass + meta requirement).
5. **Ongoing**: promotion report drives new templates from recurring bespoke shapes.

## Open questions

None blocking. Param-schema representation is **Zod** (consistency with the concept
system and reuse of the existing dependency). Templates live under
`src/components/wmi/paperQuestions/templates/`.
